# NETSCOUT

## nGeniusONE network-derived APM baseline

NETSCOUT nGeniusONE is the reference vendor for the **network-derived APM**
category in this library. NETSCOUT describes nGeniusONE as providing continuous
network and application performance monitoring and user-experience assurance,
with Smart Data derived from observed network traffic [1].

This is a service-assurance and network/application-performance baseline, not
an assertion that nGeniusONE is equivalent to host-agent APM. Its value in this
comparison is to establish what can be learned from traffic observation when
application hosts cannot be modified.

## Collection and analysis model

NETSCOUT documents nGeniusONE as consuming Smart Data generated by
InfiniStreamNG hardware/software appliances and vSTREAM virtual appliances. It
also documents server, certified-server, and virtual-appliance deployment
options, plus packet-flow infrastructure for pervasive visibility [1].

Use this as the reference for **no application-host instrumentation**, while
keeping the deployment boundary explicit:

- traffic must reach the relevant appliance, virtual probe, or sensor;
- TAP, SPAN, packet-flow-switch, cloud, or virtual capture coverage must include
  the service path being evaluated;
- the protocol, encryption boundary, packet completeness, and sensor capacity
  determine the available analysis depth; and
- product modules, deployment options, retention, and licensing must be
  confirmed for the proposed edition.

“No application-host agent” therefore does not mean “no collector or sensor.”

## Network-derived APM capability profile

| Capability | Reference interpretation | Evidence to verify in a POC |
|---|---|---|
| Application/session analysis | Protocol-specific service monitors and session views for application degradation [1] | Supported protocols, custom applications, persistent connections, and transaction identity |
| Performance indicators | Errors, latency, responsiveness, and affected clients/servers are documented outputs [1] | Exact timing boundary, request/response formula, sampling, aggregation, and error semantics |
| Service dependency mapping | Client/server relationships, application service dependencies, and network topology are documented [1] | Discovery through proxies, firewalls, load balancers, overlays, and asymmetric paths |
| Packet-derived troubleshooting | Smart Data from packet appliances/virtual appliances and on-board packet capture support troubleshooting [1] | Capture fidelity, packet loss, retention, decryption, replay, and capacity behavior |
| Multi-segment analysis | The official data sheet describes session-level, multi-segment, hop-by-hop transaction detail [2] | Current product/module support, clock accuracy, joining rules, duplicate handling, and fault localization |
| User or synthetic experience | NETSCOUT documents packet analysis of user-configurable synthetic network and business transactions [1] | Probe placement, script coverage, user-path equivalence, and separation from passive transaction evidence |

## Cross-vendor / variants

Use nGeniusONE to compare the evidence boundary of other products:

| Requirement | nGeniusONE baseline | Complementary evidence |
|---|---|---|
| No software change on application hosts | Packet-derived service and transaction observation | Host-independent capture coverage and protocol support |
| Network versus service responsibility | Network/application session indicators and dependency context | Active path tests, device counters, or agent spans for attribution |
| Multi-point service-path analysis | Ordered packet visibility and session analysis | Clock/topology/identity validation from [../techniques/npm-apm.md](../techniques/npm-apm.md) |
| Code-level root cause | Not the baseline capability | Dynatrace or another instrumented APM tool |
| Interface, routing, and device health | Complementary network/service evidence | SolarWinds NPM or equivalent device/path NPM |

Netis should be compared against this baseline for its advertised wire-data,
packet/service, and multi-point capabilities. QFlow should not be credited with
nGeniusONE's packet/session or service-assurance functions unless the relevant
IBM product documentation proves them; see [ibm.md](ibm.md).

## Design considerations

- Map every required service path to an actual capture point before claiming
  end-to-end or hop-by-hop visibility.
- Test north-south and east-west traffic separately, including cloud and
  virtualized segments, overlays, NAT, load balancing, and asymmetric routing.
- Treat encrypted traffic and unsupported protocols as explicit coverage
  questions; do not assume that application identity or transaction timing is
  available everywhere.
- Distinguish network-observed request/response time from server processing,
  database time, client rendering, and application-code time.
- Validate multi-point joining with one known transaction, duplicates,
  retransmissions, packet reordering, clock offset, capture loss, and partial
  visibility.
- Record sensor/appliance throughput, storage, retention, licensing, and
  overload behavior. Current product pages describe several deployment forms,
  but the required combination must be confirmed in the target design [1].
